# Configuration protocol (MIDI SysEx, version 1)

The Trill XIAO firmware (0.2.0 and later) can be configured over its class-compliant USB-MIDI connection. Any host that can send and receive MIDI System Exclusive can use it: the [Apple app](apple-app.md), a DAW, or a script. It does not need the CDC diagnostics port, which is not reachable from ordinary iOS apps.

> **Status:** implemented in firmware (`crates/trill-config`, `firmware/xiao-sense/src/usb.rs`) and in the app (`apple/TrillKit`). Both are checked against the same test vectors in CI. **It has not been run against hardware.**

Reference implementations: Rust [`crates/trill-config`](../crates/trill-config) (device side, plus host-side request encoders) and Swift [`apple/TrillKit`](../apple/TrillKit/Sources/TrillKit/ConfigProtocol.swift) (host side). Test vectors: [`protocol/config-v1-vectors.txt`](../protocol/config-v1-vectors.txt), generated by `make protocol-vectors`.

## Transport

| Item | Value |
|---|---|
| USB-MIDI cable | **cable 1**, the device's **second MIDI port**. Cable 0 (port 1) carries only the instrument output. |
| Direction | Host → device: requests on the port-2 *destination*. Device → host: replies on the port-2 *source* |
| Message size | At most **64 bytes**, including `F0` and `F7`. Longer messages are truncated and answered with error `TooLong` |
| Real-time bytes (`F8`–`FF`) | May be interleaved between the packets of a message, on any cable, and are ignored |
| Other status bytes | A channel or system-common status byte on cable 1 aborts an unfinished SysEx (MIDI 1.0 rule). Channel messages from the host are ignored |
| Concurrency | The device processes one request at a time. At most two replies are queued, and the reader waits when the queue is full (USB back-pressure) |

Keeping replies on a separate port means configuration traffic never shows up on the port a DAW records from. Instrument events and reply packets are interleaved per USB packet: notes are written first, and reply packets only fill spare slots, so a reply never delays a note.

## Frame

```text
F0 7D 54 52 <ver> <type> <req> <payload ...> F7
```

| Byte | Meaning |
|---|---|
| `7D` | MIDI manufacturer ID for non-commercial / educational use. **Development only.** It is not assigned to this project, and a commercial product needs its own MMA/AMEI ID. |
| `54 52` | Signature `"TR"`. Other `7D` traffic without it is ignored |
| `ver` | Protocol version, `01` |
| `type` | Requests `01`–`3F`. Replies have bit 6 set (`41`, `42`, `44`, `7F`) |
| `req` | Request ID `00`–`7F`, chosen by the host and echoed in the reply |

The device **never answers a reply-typed message** (`type & 0x40`), anything without the signature, or malformed frames. A loop that routes the device's own output back to it therefore cannot start a feedback storm. All values are 7-bit. 14-bit values are sent as `hi = v >> 7`, `lo = v & 0x7F`.

## Messages

| Request | Payload | Reply |
|---|---|---|
| `01` HELLO | host's highest version (1 byte) | `41` HELLO_REPLY |
| `02` GET_CONFIG | none (page 0), or page number (1 byte, firmware 0.4.0+) | `42` CONFIG for that page; an unknown page gets ERROR OutOfRange (detail = page) |
| `03` SET_CONFIG | 1–16 × `(param, hi, lo)` | `42` CONFIG (the page of the **first** parameter) with the values now in effect, or `7F` ERROR |
| `04` ACTION | action code (1 byte) | `44` ACTION_ACK `<code>`. Restore-defaults answers with `42` CONFIG page 0 |
| `05` TELEMETRY_START | rate in Hz, 1–100 (1 byte) | `45` TELEMETRY_ACK, then `50` TELEMETRY frames (firmware 0.3.0+, [below](#sensor-telemetry-firmware-030)) |
| `06` TELEMETRY_STOP | none | `45` TELEMETRY_ACK with rate 0 |

**HELLO_REPLY payload** (13 bytes): protocol version, firmware major, minor, patch, variant (bit 0 = `pcm-synth` build), capabilities (bit 0 SET_CONFIG, bit 1 ACTION, bit 2 persistent settings: **never set by this firmware**, bit 3 sensor telemetry: firmware 0.3.0+, bit 4 paged configuration: firmware 0.4.0+, bit 5 directional strikes: firmware 0.5.0+), max message length (64), parameter count (13 before 0.4.0, 30 in 0.4.0, 37 in 0.5.0), uptime in seconds (3 bytes, 21 bits, saturating), boot ID (2 bytes, 14 bits). The boot ID is drawn from the nRF52840 hardware RNG at reset. A changed boot ID means the device restarted and its settings went back to defaults.

**CONFIG payload:** generation (2 bytes, 14 bits, wraps), persistent flag (`00`: RAM only), then `(param, hi, lo)` for every parameter of one page in ID order. The page is implied by the IDs.

**Pages (firmware 0.4.0, capability bit 4 `0x10`).** One 64-byte reply holds at most 17 parameters (7 + 3 + 3n + 1 ≤ 64), so parameters are grouped in pages: page 0 = IDs 1–13, exactly the firmware 0.2/0.3 set and reply (an empty GET_CONFIG still returns it byte for byte); page 1 = IDs 14–30. A host that does not see bit 4 must not send page-1 parameters, `GET_CONFIG` with a payload or action 5: firmware 0.3.0 answers UnknownParam / BadLength / UnknownAction and changes nothing. The app enforces this (`ConfigSession.supportedPages`, tested against a fake 0.3.0 device), and sends one SET_CONFIG per page, at most 16 parameters each, so every CONFIG reply covers what it changed. The generation increases whenever the mapping changes, through this protocol or a diagnostics key. Unchanged values leave it as it is. Hosts should skip unknown parameter IDs, because a newer firmware may add some.

**Page 2 (firmware 0.5.0, capability bit 5 `0x20`).** IDs 31–41: directional strikes (31–37) and tilt + strike settings (38–41). `HELLO_REPLY` reports 41 parameters. The same bit also allows mode 3 (parameter 14) and scales 2–3 (parameter 4); firmware 0.4.0 rejects those values as OutOfRange. A host that does not see bit 5 must not send page-2 parameters or `GET_CONFIG` page 2; firmware 0.4.0 answers UnknownParam / OutOfRange and changes nothing. Parameter 31 takes only 0, 2, 4 or 6; odd values are rejected as OutOfRange.

**SET_CONFIG is atomic.** All values are checked first. If any parameter is unknown, repeated or out of range, nothing changes and the reply is an ERROR naming that parameter. Values are rejected, never clamped. Applying a change releases a sounding note. The engine then waits for the finger to lift, and re-centres pitch bend and resends RPN 0 if the channel, pitch mode or bend range changed. Remapping therefore cannot leave a stuck note.

**ERROR payload:** code, detail.

| Code | Name | Detail |
|---|---|---|
| 1 | BadVersion | supported version |
| 2 | UnknownType | the type |
| 3 | BadLength | payload length (max 127) |
| 4 | UnknownParam | parameter ID |
| 5 | OutOfRange | parameter ID |
| 6 | TooLong | 0 |
| 7 | UnknownAction | action code |
| 8 | DuplicateParam | parameter ID |

## Actions

| Code | Action | Effect |
|---|---|---|
| 1 | Panic | Same reset sequence as diagnostics key `p` (CC123, CC120, bend centre, pressure 0, RPN 0) |
| 2 | Recalibrate gyro | Same as key `c`. Keep the board still for about 1 s |
| 3 | LED self-test | Same as key `L` |
| 4 | Restore defaults | Firmware default mapping (RAM) and clears the orientation zero. Replies with CONFIG page 0; hosts then read the other pages they know (1, and 2 with bit 5) |
| 5 | Zero orientation (0.4.0+) | Current pitch and roll become level for controllers and tilt modes (RAM). Ignored, but acknowledged, before gyro calibration |

## Persistence

**Settings live in RAM only.** A reset, power cycle or firmware update restores the defaults, and the device reports this (persistent flag `00`, capability bit 2 clear). Nothing is written to flash. Saving settings on the device would need a flash region that is verified not to collide with the Omi/bootloader storage partition (`0xEC000`–`0xF4000`) and a power-loss-safe write scheme. Neither exists yet. Keep settings as host presets instead ([Apple app](apple-app.md#presets)).

## Sensor telemetry (firmware 0.3.0+)

A host can subscribe to a low-rate snapshot of the sensors on the same
configuration port. It is for display and logging; it never changes the
sound or the mapping. Firmware that does not set capability bit 3 answers
TELEMETRY_START with ERROR UnknownType (2); hosts should check the bit and
explain that a firmware update is needed.

- **Subscription is a lease.** TELEMETRY_START (rate 1–100 Hz; anything else is
  ERROR OutOfRange with the rate as detail) starts or re-arms it. The stream
  stops by itself 5 s after the last START, on TELEMETRY_STOP, on USB
  disconnect and on reset. Hosts renew about every 2 s while they display it.
- **TELEMETRY_ACK payload** (4 bytes): rate now in effect (0 = off), lease in
  seconds (5), frame length (54), frame format (1).
- **Lossy and lowest priority.** Frames go out on cable 1 only when no reply is
  waiting and instrument events have been sent first. A period that cannot be
  sent is counted as skipped, never queued, and values are sampled when the
  frame is built. The rate is the snapshot rate, not the IMU rate (833 Hz ODR from firmware 0.5.0).
- **TELEMETRY frame** (`50`, request ID 0, 54 bytes, payload 46 bytes). Signed
  16-bit values use 3 bytes (bits 15–14, 13–7, 6–0); 14-bit values use 2.

| Offset | Size | Field |
|---|---|---|
| 0 | 1 | format (1) |
| 1 | 2 | sequence, 14 bits, wraps |
| 3 | 3 | device time of the IMU sample, ms, 21 bits, wraps |
| 6 | 1 | flags: 1 IMU valid, 2 gyro calibrated, 4 touching, 8 new IMU sample since the previous frame, 16 safe mode |
| 7 | 1 | IMU state, 8: Trill state (0 off, 1 starting, 2 running, 3 not detected / retrying, 4 disabled) |
| 9 | 9 | acceleration X, Y, Z in mg (i16) |
| 18 | 9 | rotation rate X, Y, Z in 0.1 °/s (i16) |
| 27 | 6 | pitch, roll in 0.01° (i16) |
| 33 | 4 | touch position, touch size, 0–16383 = 0–1 (meaningful only with flag 4) |
| 37 | 2 | IMU samples counter, 14 bits |
| 39 | 2 | tap counter, 14 bits |
| 41 | 1 | gyro calibration counter, 7 bits |
| 42 | 2 | skipped frames, 14 bits |
| 44 | 2 | Trill frames counter, 14 bits |

Values saturate at the i16 range. When the IMU is not running or a value is
not finite, flag 1 is clear and the IMU fields are 0; hosts must not plot
them. Pitch = atan2(−ax, √(ay²+az²)) (±90°) and roll = atan2(ay, az) (±180°)
in the IMU's own axes, smoothed with the gyro; there is no yaw (no
magnetometer). Shared fixtures: `protocol/telemetry-v1-frames.txt`.

## Safety properties

- A message can only read or change the 30 parameters above and trigger the 5 actions. No message addresses memory, pins or flash.
- Parsing is bounded: fixed 64-byte buffers, no allocation, and work proportional to the message length. It runs on the USB executor, and engine access is a short critical section, the same as the diagnostics keys. It never waits on sensors.
- A fuzz test pushes 200 000 random packets through reassembly and handling. It checks that nothing panics, that every reply is a well-formed SysEx of at most 64 bytes, and that every applied config is already sanitized.

## Host guidance

- Use one request in flight. Match replies by request ID and give up after a timeout (the app uses 1 s). Late replies with an old ID are ignored.
- Send only to the destination the user selected. Do not broadcast SysEx to every destination.
- Start with HELLO. If the reply's version is not 1, stop.
- Send each SysEx as one message (CoreMIDI: `MIDISendEventList` with sysex7 UMPs). Real-time bytes between UMPs are handled. In a hardware test on macOS 26, a single legacy `MIDIPacket` with an `F8` byte embedded inside the SysEx bytes never reached the device intact (no reply), while the same request as sysex7 UMPs with a separate real-time UMP between them was answered. The firmware's handling is unchanged; this is a host-side packaging rule.

## Example

From the vectors (defaults, generation 0):

```text
→ F0 7D 54 52 01 03 03 01 00 02 05 00 01 F7      SET_CONFIG req 3: channel=2 (MIDI ch 3), pitch=steps
← F0 7D 54 52 01 42 03 00 01 00 01 00 02 ... F7  CONFIG req 3: generation 1, not persistent, all 13 values
```
