# Changelog

All notable changes to this project are documented here. Versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added
- **Instrument view (prototype, Mac, iPhone and iPad):** a handpan you play by striking the sensor on a stick or hanging from a string. Open it from Presets › Open instrument view. Strikes are detected in 8 horizontal directions, each playing one tone field. Tilt past 30° plays ring 2 and past 60° the ding; both are adjustable. Velocity comes from strike strength. Eight handpan scales can be picked by name, with sources: Kurd, Celtic Minor, Integral, Hijaz, Pygmy, Amara, Equinox and La Sirena. Any ding from E2 to A3 can be chosen, with a clockwise or alternating layout. **Up** is adjustable: pick ±X/±Y/±Z or use Set current pose as up. Directions come from measured gravity, so they stay right upside down (shown as INVERTED). Roll about the up axis is counted over several turns instead of wrapping at 360°. One screen holds a compass ring with note labels, the live push against the threshold circles, last-hit and recent-strike marks, tilt zones, a roll readout and a 3 s strength trace, plus compact controls (threshold, swing, sensitivity, debounce, refractory, tap assist, ring tilts, up, N). Detection runs in the app from telemetry: the new TrillKit `ImpulseEngine`, `Handpan` and `InstrumentRunner` have unit tests on synthetic IMU traces (upright, upside down, all 8 directions, tilt rings, multi-turn roll, debounce and refractory, stick and string swing, tap assist). **App-generated MIDI** plays through the app's own CoreMIDI source "Trillium Instrument". No firmware change is needed. Telemetry runs at 100 Hz while it's on; latency is about 10–40 ms (see `docs/instrument-view.md`). The iPad screenshot job captures the view with synthetic motion.
- **Startup intro:** the Light trails rose curves (r = cos 3θ) draw themselves, then the lockup appears, in 1.2 s or less. Tap to skip. With Reduce Motion the intro appears without drawing. The Rhodonea mark itself is not animated.
- `docs/design-themes.md`: a design note on alternate accents for people who dislike orange, and on clarity in dark venues (not implemented).

## [0.8.0] - 2026-11-19

### Added
- **Bluetooth on/off controls (Bluetooth build):** two separate switches, **Discoverable** (advertising) and **Bluetooth MIDI** (the MIDI service), set from Settings › Detected hardware or Settings › Connection, stored on the board (one flash page at `0xEC000`, append-only log; nothing outside that page is written) and both on by default. Discoverable off stops advertising at once and keeps a current link; Bluetooth MIDI off disconnects a host and sends no MIDI over Bluetooth. USB MIDI always works. New protocol actions 10–13 (9 stays unassigned), answered with the new `47` STATUS. See `docs/ble-midi.md`.
- **Battery detection and level (every build):** the firmware reads the XIAO's battery divider (P0.31/AIN7) and charger status (P0.17) once a second and reports battery present/absent, voltage, approximate percent (LiPo curve) and charging through the new `07` GET_STATUS / `47` STATUS (HELLO variant bit 5, `0x20`). Presence on USB power is a heuristic (charger-status toggling, voltage ripple and range over 10 s) with documented limits. The Bluetooth build also offers the standard Battery Service (`0x180F`). See `docs/battery.md`.
- **Bluetooth needs a battery:** the Bluetooth build advertises and keeps a link only while a battery is detected; the app shows "Bluetooth needs a battery" otherwise.
- **App:** Settings › Detected hardware shows the battery (present, %, V, charging) instead of "not reported", the Bluetooth switches with "Discoverable: on/off" and "Bluetooth MIDI: on/off/connected", and a battery indicator; a board with a battery and Bluetooth is listed as T1. New `crates/trill-board` (battery maths, presence heuristic, settings record) with host tests; new protocol vectors and Swift decode tests.
- **MIDI over Bluetooth LE (build option, `ble-midi`):** a second application-only UF2 (`xiao-sense-fw-ble-midi-<version>.uf2`) for battery-powered boards (T1 and up). It enables the S140 SoftDevice already in flash (never written) and advertises the standard BLE-MIDI service as `Trillium XXXX` (low 16 bits of the chip's BLE address). It sends the same instrument MIDI as USB, which keeps working at the same time; configuration, telemetry and the microphone test stay on USB. HELLO variant bit 4 (`0x10`) reports it. New `crates/ble-midi` with timestamp framing and test vectors. See `docs/ble-midi.md`. Not yet tested on hardware.
- **Bluetooth MIDI in the app:** Settings › Connection has a Bluetooth MIDI… button (iPhone and iPad: the system Bluetooth MIDI panel; Mac: the system panel or Audio MIDI Setup). Detected hardware shows "BLE MIDI" and the button when the firmware reports it. The MIDI monitor uses a Bluetooth Trillium source when no USB instrument port is present, and the port pickers mark Bluetooth sources. The app gains a Bluetooth usage description, and the Mac app the sandbox Bluetooth entitlement, for the system pairing panel.

The splash uses the approved lockup, and Home and About use the Rhodonea mark instead of the previous code-drawn petals; `apple/scripts/make_app_icon.swift` and `make apple-icon` are removed. - **Vision brainstorm** in `docs/vision.md`, linked from the roadmap, to capture ideas for later prioritization.
- README header uses the wordmark lockup (light and dark variants); release notes start with the kit's release header.
- **App Store export compliance:** both app Info.plist files set `ITSAppUsesNonExemptEncryption` to NO. The apps use only OS-provided Bluetooth; they include no custom cryptography.

Decision 2026-11-19: BLE-MIDI firmware is published in public releases; the image contains no Nordic code and uses the SoftDevice already on the board.
- **Battery safety:** the firmware now drives P0.14 (READ_BAT) LOW from boot in every build and never releases it, as Seeed requires while the battery may be charging; 0.7.0 and earlier left it floating. P0.13 (charge current) is still not driven, so charging stays at about 50 mA.
- HELLO variant bit 4 (`0x10`) now means "Bluetooth stack available"; whether the board is advertising or connected comes from STATUS.
- Firmware: the IMU executor moved from `EGU2_SWI2` to `EGU3_SWI3` and peripheral interrupts are no longer left at priority 0, in every build (required next to the SoftDevice). The memory layouts moved to `firmware/xiao-sense/link/`.

### Fixed
- **Microphone test showed no chart and played nothing (Mac app 0.7.0):** the app opened the PCM port (`/dev/cu.usbmodem…`, interface 5) with the default terminal line discipline, which is line-buffered and rewrites or drops control bytes (CR, NL, erase, kill, EOF, start/stop). Binary `TRPC` frames never passed their CRC, so no block reached the level chart or play-through. The port is now opened read-only, non-blocking, in raw mode with DTR raised; the line speed is never changed. The panel reports when no data arrives within 2 s. Only the app changes; firmware 0.7.0 is unchanged. Regression tests run a frame full of control bytes through a pseudo-terminal in both modes.
- **Board changes are noticed:** the app watches the board's USB enumeration (macOS) and the HELLO boot ID. When a board is unplugged, swapped or restarted it stops the microphone test, clears the sensor history and reads HELLO again.

### Added
- **Detected hardware in Settings:** model in the T0/T1/T2/F1 lineup plus a capability list, firmware version and build, USB ID, motion sensor, Linear sensor (state, 30 channels, touches), microphone, battery and BLE (not reported by current firmware), transport and serial ports (diagnostics and PCM). While Settings is open the app requests a slow sensor stream to keep it current.
- **Sensors layout follows the board:** charts appear only for sensors that are present. A missing Linear sensor (reported by the firmware as retrying) or motion sensor collapses to one line under *Not available*.

## [0.7.0] - 2026-11-18

### Added
- **Multi-touch telemetry and Sensors chart:** the firmware already decoded up to five 1-axis contacts from a Trill Flex or Bar, but only the first was published. It now sends a companion SysEx (`51`, advertised as variant bit 3) with each format-1 telemetry frame, listing up to five positions and sizes, paired by sequence number. Format 1 is unchanged and still carries the first touch, so older apps keep working. Default MIDI is unchanged (one voice, first touch). The Sensors view labels the strip **Linear sensor** and draws every reported contact. Shared fixtures: `protocol/telemetry-touches-v1-frames.txt`.
- **Model lineup and Trillium Zero as the starting point** (docs only): T0 is one Seeed Studio XIAO nRF52840 Sense on a USB cable (USB-MIDI, free Trillium app). T1 is T0 plus a battery and BLE (built and tested on an early Omi DIY board). T2 is T1 plus a better LED and buttons (planned). F1 is T2 plus a Bela Trill Flex linear touch sensor (planned; only breadboard T0 plus Flex has been tested). Other combinations are possible; a board is described by model plus a capability list. The README and `docs/hardware/trillium-zero.md` now lead with T0. `hardware/README.md` records the lineup. The revision A drawings under `hardware/t2/` and `hardware/f1/` are unchanged and are mapped to the planned T2 and F1; those folders are not renamed.
- **Roadmap plans** (docs only, no app or firmware changes): UI wording should say instrument/configuration rather than different "sounds"; the Sensors chart label "Bela" should become "Linear sensor". Firmware will self-report model and capabilities; the app will record each board by serial number. First-time setup stays on USB; BLE-MIDI discovery comes after that (still subject to the existing licence note).
- **Microphone test switch:** the Sense onboard PDM microphone can be switched on from Sensors in Trillium as a testing-only capture path, not part of any instrument or configuration. It is off by default; the power pin is held low when it is off. When on, the firmware captures 16 kHz 16-bit mono PCM and sends it as framed `TRPC` on the USB PCM port (now present in the default build; PID `1209:0003`). The Mac app shows a live level chart and can play the signal through the system output. Actions 7 and 8 start and stop capture; HELLO variant bit 2 is set when the path is available. USB Audio Class, BLE audio, recording and reuse, and iOS play-through are still deferred. If the optional `pcm-synth` debug synth is built, it shares the same PCM port and is pre-empted while the microphone is on.
- **Microphone research** (`docs/research/microphone.md`) records the constraints behind this path.

## [0.6.0] - 2026-11-15

### Added
- **The app installs firmware** (macOS; iOS untested on a device): each Trillium build carries the firmware of its own version (`make apple-firmware`; CI and releases bundle the UF2 from the same commit). The app identifies the board and its firmware, offers an update when the board runs older firmware, says "update the app" when it runs newer, and spots a new XIAO with other firmware or a waiting bootloader drive. Installs back up `CURRENT.UF2` plus an app-only restore image first, use the `xiao_uf2.py` safety rules, then reconnect and check the version.
- **Firmware action 6, enter bootloader** (capability bit 6): restarts into the UF2 bootloader so updates need no RESET double-press. Writes no flash.
- **Board report** (capability bit 6, variant bit 1): the firmware probes the IMU at boot (0x6A/0x6B). A XIAO nRF52840 without the motion sensor reports `imu=absent`, scans the internal bus once for diagnostics, switches the sensor supply off and stops retrying; the LED shows no fault and the app says the board is not supported. Variant bit 2 is reserved for the microphone.

### Changed
- *Connect automatically* is on by default.
- Release notes tell users to install firmware from the app, and to use the Board-ID that `xiao_uf2.py info` prints (bootloader 0.9.0 reports `nRF52840-SeeedXiaoSense-v1`, 0.6.1 `Seeed_XIAO_nRF52840_Sense`).

### Tested on hardware
- Firmware 0.6.0 (before action 6 was added) on a plain XIAO nRF52840 (bootloader 0.9.0): `imu=absent`, internal bus scan found no devices, USB MIDI up, no fault LED.
- App install on the XIAO nRF52840 Sense (bootloader 0.6.1), macOS, unsigned build: 0.5.0 → 0.6.0 with one click after a RESET double-press (0.5.0 has no action 6), no file or drive picked; backup written to Application Support (its app-only image matches the `xiao_uf2.py` split); the board reconnected reporting 0.6.0, IMU running, calibrated.
- Factory-new XIAO nRF52840 Sense (bootloader 0.6.1, Seeed's Arduino demo firmware), macOS, unsigned build: Install in the app, one RESET double-press; Seeed's firmware backed up (`app-only.uf2` holds the Arduino image), board came back with Trill firmware 0.6.0 with the IMU at 0x6a, calibrated, and the **Trill sensor detected (`trill=run`)** for the first time.

### Not yet tested on hardware
- **Reinstalling from the app without RESET** (action 6, Settings › Firmware › *Reinstall firmware 0.6.0*) is not yet fully tested on hardware; it will be tested with this release. If the board does not come back, double-press RESET and install again.
- iOS; a signed, sandboxed build.

### Changed (0.5.0)
- Firmware 0.5.0 (with the calibration fix) has been flashed on one XIAO Sense: it boots, the IMU runs at ≈ 790 samples/s (833 Hz nominal), USB MIDI works and a forced recalibration finishes in about 1 s. Directional strikes and the new app screens have not yet been tried on hardware.
- Firmware: the IMU task runs on its own interrupt executor (`EGU2_SWI2`, P7) so blocking Trill I²C reads in thread mode no longer delay IMU samples; IMU at **833 Hz** (was 416 Hz) and accelerometer **±8 g** (was ±4 g) so hard taps do not clip. Gyro calibration uses 800 samples (≈ 1 s). Worst-case motion-to-sample wait falls from ≈ 2.4 ms plus a possible 2.3 ms Trill read to ≈ 1.2 ms (calculated, not measured).
- `trill-config`: duplicate-parameter tracking widened to 64 bits (parameter IDs above 31).
- Gyro calibration judges stillness around the run's own mean (each axis within 4 dps, raw |ω| < 15 dps) instead of raw |ω| < 3 dps. Found on hardware: the first 0.5.0 build never calibrated on the user's board (bias ≈ 2.6 dps plus 833 Hz noise kept breaking the run). The sensor's zero-rate spec is ±10 dps, so the old rule could fail on any board.

### Changed
- The Apple companion app is now named **Trillium** (`Trillium.app`, schemes `TrilliumMac`/`TrilliumIOS`, artifacts `Trillium-macOS-…`, `trillium-*` CI artifacts, test kit `Trillium-<version>-<commit>`). Trill remains the name of the Bela sensor, the firmware, USB device, protocol, `TrillKit` package and repository. Bundle ID unchanged (`com.nymble.trill`).

### Fixed
- **Tap percussion stopped after 35.8 min** of continuous calibration (and returned 35.8 min later): the 1 s arm delay used a signed `u32` µs comparison that flips at 2³¹ µs. Now a latch. The same class of bug could hold a controller unchanged for over 35.8 min, or a sensor returning after a 35.8 min gap; elapsed times are now `wrapping_sub` intervals and only samples up to 1 s older are treated as backwards. Tests at 37/60/72/100/150 min and across the u32 wrap. (Firmware 0.4.0; not yet run on hardware.)

- USB layout: two MIDI cables per direction; `bcdDevice` 0x0200. Workspace version 0.3.0 (0.2.0 added configuration; `bcdDevice` stays 0x0200 because the USB layout did not change).
- XIAO Sense firmware: the on-board synth, its high-priority audio task and the PCM CDC port moved behind the optional `pcm-synth` feature. The default build renders no audio. USB PID changed from 1209:0001 to 1209:0002 (default) / 1209:0003 (`pcm-synth`).
